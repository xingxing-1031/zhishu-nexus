# 卡片 01：项目全貌与当前边界

## 一句话定位

这是一个面向零售运营人员的可审计数据分析 Agent。运营人员用自然语言提问，系统分析订单、商品、渠道和退款数据，同时保留 SQL、执行过程和数据来源，方便检查结论。

“可审计”不是页面能聊天，而是回答可以追溯：

```text
自然语言问题
-> 使用了什么业务口径和表结构
-> 生成了什么 SQL
-> SQL 是否经过安全校验
-> 查询了哪些数据
-> 如何得到结论和图表
```

## 它解决的业务问题

运营人员经常需要回答：

- 最近 30 天哪个渠道销售额最高？
- 哪些商品退款金额较高？
- 各渠道的已支付订单数是多少？

传统流程需要找懂 SQL 的数据人员，沟通口径后再取数。本项目的目标是缩短这个过程，同时避免大模型直接执行危险 SQL 或编造结果。

## 已经完成什么

- Python 项目结构、虚拟环境和 pytest。
- `Order`、`Product`、`Refund`、`AnalysisRequest` 领域模型。
- 四张核心业务表的 ER 设计和 SQL 练习。
- FastAPI 健康检查与分析请求校验接口。
- 15 项自动化测试。

## 还没有完成什么

当前项目还没有接入 PostgreSQL，没有执行真实业务 SQL，也没有 LangGraph、RAG 和完整 Agent 工作流。因此现在只能称为“基础后端与领域模型已完成”，不能声称 Agent 已经可用。

接下来的主线是：

```text
PostgreSQL 真数据
-> 安全查询服务
-> LangGraph 分析流程
-> 指标与 Schema RAG
-> 审计、权限和容错
-> 评测与交付
```

## 自测

### 1. 项目的核心用户是谁，解决什么问题？

<details>
<summary>展开标准答案</summary>

核心用户是不熟悉 SQL 的零售运营人员。项目让他们用自然语言查询订单、商品、渠道和退款数据，减少反复找数据人员取数的成本，同时保留 SQL、执行过程和数据依据，便于核对结果。

</details>

### 2. “可审计”具体指什么？

<details>
<summary>展开标准答案</summary>

结论能够追溯到业务口径、表结构、生成的 SQL、SQL 校验结果、实际查询数据和执行步骤，而不是只给出一段无法核实的自然语言答案。

</details>

### 3. 为什么现在还不能说完整 Agent 已经完成？

<details>
<summary>展开标准答案</summary>

因为目前只完成领域模型、SQL 设计和基础接口，尚未接入 PostgreSQL 真数据、SQL 安全执行、LangGraph 工作流、RAG 和完整审计链路。

</details>
