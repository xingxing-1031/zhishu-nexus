# W5-3 手机学习卡：超时、重试、幂等与降级

## 1. 本阶段解决什么问题

W5-2 解决了高风险查询需要人工审批，但真实服务还会遇到网络波动、模型暂时不可用、数据库超时、进程崩溃和前端重复提交。

W5-3 的核心不是“所有错误都重试”，而是先判断失败性质，再选择有限重试、直接拒绝、失败返回、幂等处理或降级。

## 2. 四类失败处理

```text
临时外部故障 → 有限重试 + 指数退避
确定性安全错误 → 直接拒绝
核心查询没有可信结果 → 失败返回
副作用可能被重复执行 → 幂等键 + 唯一约束
可信表格已有、表达层失败 → 降级返回表格
```

示例：

```text
模型 503 → 最多重试几次
SQLGlot 检测 DELETE → rejected，不重试
PostgreSQL statement_timeout → failed，不原样重跑
审批日志写成功后崩溃 → 重放时去重
SQL 成功但总结模型失败 → rows 保留，status=degraded
```

## 3. 为什么不能所有错误都重试

错误可以分为：

- **瞬时错误：** 429、临时 503、网络超时、连接重置，过一会儿可能恢复。
- **确定性错误：** DELETE、越权字段、无效 JSON Schema、非法表字段，重试不会改变错误性质。
- **业务资源错误：** 查询超过 `statement_timeout`，原样重跑通常还会继续占用资源。

重试必须有最大次数和总时间预算，不能无限循环，也不能把安全拒绝伪装成网络故障。

## 4. 指数退避

连续立即重试会让故障服务受到更多请求。指数退避逐渐拉长等待：

```text
第 1 次重试：0.5 秒
第 2 次重试：1 秒
第 3 次重试：2 秒
```

实际系统还可以加入少量随机抖动，避免大量客户端同时重试。当前模型适配器只对 `408/429/5xx` 和网络超时重试，400 等永久错误不重试。

## 5. 四层超时

```text
连接超时：能否连接服务
单次调用超时：一次模型调用最多多久
statement_timeout：一条 SQL 最多执行多久
工作流总预算：整条请求最多多久
```

单次调用 30 秒不代表整个工作流只有 30 秒。规划、检索、SQL 生成、纠错重试、数据库和总结会累加，所以每个节点都要使用剩余总预算：

```text
实际 timeout = min(组件上限, 工作流剩余时间)
```

剩余时间不足以完成下一次重试时，应立即失败或降级，而不是再启动一个超出预算的调用。人工审批等待不属于一次主动工作流调用，恢复审批时会重新建立预算。

## 6. 审计事件幂等

如果节点已经写入 `pending` 审计，随后在保存 Checkpoint 前崩溃，恢复会重跑节点。普通 INSERT 会产生重复日志。

幂等键要表示一个具体逻辑事件：

```text
approval:{request_id}:pending
approval:{request_id}:resolution
```

数据库对 `event_key` 建唯一索引，重复写入使用：

```sql
ON CONFLICT (event_key) DO NOTHING
```

不能只把 `request_id` 设为唯一，因为同一请求合法地需要记录 pending 和最终 approved/rejected 两个事件。

查询审计使用由请求、SQL、状态等内容生成的稳定哈希作为事件键，重放时忽略变化的耗时字段。

## 7. API 请求幂等

前端可能因为没有及时收到响应而重复提交同一 `request_id`。因此服务登记：

```text
request_id
request_fingerprint
user_id / access_role
running / pending / completed / degraded / rejected / failed
```

处理规则：

```text
相同 request_id + 相同请求内容 → 返回已有状态或结果，不重新运行
相同 request_id + 不同请求内容 → 409 Conflict
首次请求 → 原子登记后启动工作流
```

`thread_id` 只负责从 Checkpointer 找状态，不能单独替代 API 幂等登记和请求指纹校验。

## 8. 什么可以降级

降级的前提是已经有可信核心结果：

```text
SQL 已安全执行并返回 rows
→ 总结模型失败
→ 保留 rows，返回固定降级说明
```

此时应区分：

```text
query_status = succeeded
overall_status = degraded
```

如果 SQL 还没生成、没通过安全校验或没有执行，就没有可信数据，不能根据自然语言猜一个估算结果。

当前还增加了数字落地校验：总结中出现的数字必须能在问题、结构化计划或真实 rows 中找到。模型把 `800.00` 改成 `801.00` 时，系统会降级而不是返回错误数字。

## 10. 自测题

1. 模型返回 503 和 SQLGlot 检测 DELETE，为什么处理方式不同？
2. 为什么重试必须有最大次数？
3. 指数退避解决什么问题？
4. 单次模型调用超时和工作流总预算有什么区别？
5. 总预算只剩 2 秒、下一次调用上限 30 秒时，应该怎么做？
6. 为什么 `statement_timeout` 后不能原样无限重试？
7. 为什么审批日志不能只用 request_id 唯一？
8. `approval:{request_id}:pending` 和 `approval:{request_id}:resolution` 分别表示什么？
9. `ON CONFLICT DO NOTHING` 在这里解决什么问题？
10. 为什么 thread_id 不能单独替代 API 请求幂等？
11. 相同 request_id 但问题内容不同，为什么返回 409？
12. SQL 成功、总结失败时为什么可以降级？
13. SQL 尚未执行时为什么不能返回估算数据？
14. 模型把查询结果中的 800 写成 801，系统如何处理？

## 11. 自测题标准答案

1. 503 可能是瞬时故障，DELETE 是确定性安全错误；前者有限重试，后者直接拒绝。
2. 防止无限试错、请求堆积、Token 浪费和数据库/模型服务压力扩大。
3. 拉开重试间隔，避免连续请求冲击故障服务；抖动还能避免客户端同步重试。
4. 单次超时限制一个调用，总预算限制整条工作流；多个节点和重试会累加。
5. 不再发起 30 秒调用，立即失败或在已有可信结果时降级。
6. 相同查询通常仍会超时，继续占用数据库资源；应记录 failed 并交给后续策略处理。
7. 一个请求至少需要 pending 和最终审批两个事件；只用 request_id 会让后续事件冲突或覆盖历史。
8. 前者是进入审批的事件，后者是唯一的最终批准或拒绝事件。
9. 恢复重放时重复事件不会产生第二条日志。
10. thread_id 只定位 Checkpoint，不能阻止 API 重复启动，也不能验证请求内容是否相同。
11. 同一个标识代表两个业务请求会造成结果和审计混乱，必须让客户端换新 request_id。
12. rows 已经由安全 SQL 和 PostgreSQL 验证，失败的是表达层，不应丢弃可信数据。
13. 没有经过计划、证据、安全校验和真实数据库的结果，估算可能造成业务错误。
14. 数字落地校验拒绝无依据的 801，返回真实表格和固定降级说明，并记录错误原因。
