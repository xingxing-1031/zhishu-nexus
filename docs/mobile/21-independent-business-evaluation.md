# W6-1 手机学习卡：独立业务评测集

## 1. 本阶段解决什么问题

端到端链路能够运行，不代表它能稳定回答真实业务问题。只测试 SQL
是否合法，也不能证明销售额、订单数或退款金额算对了。

W6-1 建立一套独立基准，用固定输入和人工 Gold 答案回答：

```text
系统到底答对了多少？
如果答错，错误发生在哪一层？
```

## 2. 为什么最终业务结果最重要

两条 SQL 可以写法不同但结果等价，也可能都能执行却采用了不同业务
口径。因此不能只比较 SQL 字符串。

评测需要分别检查：

```text
用户意图 -> AnalysisPlan
业务依据 -> RetrievalEvidence source_id
执行边界 -> 安全、权限、审批状态
真实答案 -> PostgreSQL 精确结果行
表达结果 -> 最终回答和图表
```

分阶段评分能快速定位是计划、检索、SQL、执行还是总结出了问题。

## 3. 什么是 Gold 答案

Gold 是评测前由人工确定的标准答案。可信结果由人工审核的参数化 SQL
在固定数据库快照上执行得到，不能让被评测模型自己生成标准答案。

否则相当于让考生给自己的试卷判分，模型的错误可能同时进入预测和
答案，最后得到虚假的高分。

## 4. 固定时间和数据库快照

“最近 30 天”会随真实日期变化。评测固定：

```text
reference_time = 2026-08-16 12:00:00+08:00
timezone = Asia/Shanghai
snapshot = retail-demo-evaluation-2026-08-16-v1
```

因此同一条题目今天、明天或在 CI 中执行，都应得到相同答案。

Gold 验证脚本只在事务中临时设置绝对时间，核对完成后 `rollback`，不
修改开发数据库的长期状态。

## 5. 60 条用例怎样组成

```text
40 条 development：用于发现问题和改进系统
20 条 frozen holdout：系统固定后只做最终评估
```

业务类别为：

```text
15 条基础分析
15 条复杂分析
10 条不支持的问题
10 条权限与审批边界
10 条确定性故障与容错
```

正确拒绝也是成功。例如数据库没有库存字段时，拒绝库存问题比编造
库存数字更可靠。

## 6. 一条用例记录什么

成功或降级用例包含：

```text
question / access_role / expected_outcome
expected_plan
expected_source_ids
gold_sql / expected_rows
expected_chart_type
rationale / tags
```

拒绝、失败和待审批用例不伪造结果，而是记录 `expected_reason_code`。
故障用例还记录组件、第几次调用和错误类型。

## 7. development 与 holdout

development 的失败可以用来调提示词、检索、规则和代码。holdout 用于
估计系统面对未见问题时的效果，不能一边看答案调参，一边继续把它
叫作独立测试。

一旦根据某条 holdout 失败修改系统，这条题已经泄露，应转入开发证据，
并重新建立没有参与调优的 holdout。

## 8. 为什么不比较 SQL 原文

以下 SQL 可能语法不同但业务结果一致：

```sql
SELECT COUNT(*) FROM orders WHERE status = 'paid';

SELECT COUNT(order_id) FROM orders WHERE status = 'paid';
```

因此 W6-2 会比较计划、证据、安全结果和精确结果行，而不是要求模型
逐字复现人工 SQL。

## 9. 当前边界

W6-1 只建立并验证基准，不在本阶段公布模型得分。W6-2 才会运行基础
方案、加入检索和加入 Reranker 的对照实验，并生成错误分类报告。

## 10. 自测题

1. 为什么能执行的 SQL 不一定业务正确？
2. 为什么 Gold 结果不能由被评测模型生成？
3. 为什么相对日期必须绑定固定 reference_time？
4. 为什么数据库快照也必须固定？
5. development 和 holdout 分别用来做什么？
6. 看过 holdout 错题后针对它改提示词，会发生什么？
7. 为什么正确拒绝也应计为成功？
8. 为什么不逐字比较模型 SQL 和 Gold SQL？
9. 为什么需要分别评估计划、检索、SQL 和最终结果？
10. resilience 用例为什么要指定 occurrence？

## 11. 自测题标准答案

1. SQL 可能用了错误状态、价格字段、JOIN 或聚合口径，即使语法合法也会得到错误业务数字。
2. 模型可能把同一个错误同时写进预测和标准答案，评测会失去独立性。
3. 否则“最近 30 天”的起止时间每天变化，结果无法复现和比较。
4. 数据变化也会改变答案；固定时间但不固定数据仍然无法复现。
5. development 用于诊断和改进；holdout 用于系统固定后的独立最终评估。
6. 发生测试泄漏，这条题不能继续作为独立 holdout 证据。
7. 当数据、指标或权限不足时，拒绝能避免编造和越权，符合预期业务行为。
8. 等价 SQL 可以有不同写法，应比较业务语义、安全边界和精确结果。
9. 这样可以知道具体在哪一层出错，并进行针对性修复。
10. 指定组件和调用次数才能稳定复现同一故障路径，避免随机测试。
11. 请求没有可信查询结果，填写数据会掩盖正确的拒绝或失败语义。
12. W6-1 建立并验证基准；W6-2 才运行系统、计算分数并分析错误。
