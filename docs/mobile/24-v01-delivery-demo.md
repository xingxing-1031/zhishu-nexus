# W6-4 手机学习卡：架构、评测报告与 v0.1 演示

## 这一步解决什么问题？

前面的里程碑证明功能逐层可靠，W6-4 要把这些证据组织成别人能理解、能运行、能复核的项目交付。重点不是再堆一个框架，而是让面试官或运营人员能沿着一条真实请求看懂：谁调用了什么、依据来自哪里、为什么 SQL 能执行、结果怎样变成图表。

## 架构图应该表达什么？

架构图不是把文件名全部堆在一起，而是表达边界和数据流：

```text
运营人员
-> FastAPI / v0.1 前端
-> 可信身份
-> LangGraph State 与节点
-> AnalysisPlan
-> RetrievalEvidence
-> SQLGlot + 业务一致性校验
-> 权限/审批
-> PostgreSQL
-> rows + ChartSpec + Trace
```

图中还要标出 Checkpointer、审计和 Trace，因为它们解释了系统如何恢复、谁做了什么以及故障发生在哪里。完整图在 `docs/ARCHITECTURE.md`。

## 评测报告应该保留哪些证据？

报告不能只写“准确率 100%”。至少要说明：

```text
实验唯一变量
固定模型、数据快照、参考时间和策略
案例数量与运行次数
plan / evidence / SQL / outcome / rows / chart 阶段分数
延迟、重试和结果状态分布
answer_score 是否适用
development 与 holdout 的边界
```

本项目的 W6-2 报告来自真实 JSON 原始记录，不能手工挑最好的一次，也不能把 `answer_score=None` 写成 0 分。三方案核心打平时，只能说本轮正确性相同、成本不同，不能直接宣布某个方案最终最好。

## v0.1 前端怎样保持安全？

前端只是调用边界，不拥有安全判断能力：

- `/analysis/stream` 负责启动完整 LangGraph，而不是直接调用 SQL 模型；
- SSE 只展示后端发来的节点状态；
- 表格使用后端可信 rows，图表使用后端 `ChartSpec`；
- Trace 通过受权限保护的接口读取；
- 高风险请求显示 SQL 和审批原因，但 analyst 不能执行批准操作；
- 浏览器不能在请求体里把自己伪装成 admin，身份来自服务器配置。

前端遇到总结失败时仍可展示可信表格，并显示降级原因；遇到 SQL、权限或数据库失败时显示明确状态，不自行猜一个答案。

## 自测题与标准答案

1. **为什么架构图不能只列文件名？** 因为文件名不能说明请求、状态和权限如何流动；架构图要表达组件职责、数据流和安全边界。
2. **为什么评测报告不能只写核心通过率？** 总分不能定位计划、证据、SQL、结果或图表哪一层出错；还需要阶段分数和原始运行条件。
3. **前端为什么不能直接调用 SQL 生成模型？** 这样会绕过计划、证据、SQLGlot、业务一致性、权限和审批；前端必须调用完整工作流接口。
4. **图表由谁决定？** 后端根据经过校验的 AnalysisPlan 和真实 rows 生成 ChartSpec，前端只按规格渲染，不重新计算销售额。
5. **SSE 和普通分析接口有什么区别？** 普通接口等全部完成后一次性返回；SSE 在同一条完整工作流运行期间持续发送节点状态，最后发送结果或审批/拒绝事件。
6. **总结模型失败但 rows 正确时，前端怎么处理？** 保留可信表格和图表，显示 `degraded` 及降级原因，不伪造自然语言结论。
7. **为什么演示不能代表生产部署？** 当前只有本地可信身份、10 条种子数据和 development 结果；正式登录、Secret、并发、监控、备份、云部署和 holdout 验收还未完成。
8. **W6-2 的三个方案本轮都 100%，如何选方案？** 先说明正确性打平，再比较重复实验中的稳定性、延迟、成本和独立数据泛化，不能凭一次 development 结果宣称 reranker 最好。

## 三分钟口述标准参考

我正在开发一个面向零售运营人员的可审计数据分析 Agent。W6-4 的目标不是继续增加框架，而是把已有的代码、测试和评测结果组织成可理解、可复核和可演示的 v0.1 交付。架构图表达一条真实请求如何从前端进入 FastAPI，再进入 LangGraph；工作流把自然语言变成 AnalysisPlan，按计划检索指标和 Schema 证据，生成 SQL，经过 SQLGlot 只读校验和业务一致性校验，再经过权限和高风险审批，最后访问 PostgreSQL，返回 rows、ChartSpec 和 Trace。Checkpointer 负责节点边界的恢复，Audit 记录业务行为，Trace 记录系统运行细节。

评测报告不能只写一个漂亮的准确率。本项目固定 qwen3:4b、development 数据集版本、PostgreSQL 快照、参考时间、时区、安全与权限策略，只替换检索方案；三个方案各运行 40 条真实 LangGraph，共保存 120 条原始记录。独立评分器分别检查 plan、evidence、SQL、outcome、rows 和 chart，answer 单独评分。最终三个方案核心阶段都是 100%，baseline 延迟最低、reranker 最高，所以只能说本轮正确性打平，不能包装成通用 Agent 准确率；`answer_score=None` 也表示尚未配置独立回答评审。

v0.1 前端是 FastAPI 的同源静态界面。它通过 `/analysis/stream` 调用完整工作流，使用 SSE 展示计划、检索、校验、执行和总结状态，使用后端返回的 rows 和 ChartSpec 渲染表格和图表，并通过受权限保护的接口查看 Trace。高风险请求会展示审批 SQL 和原因；analyst 的按钮被禁用，浏览器不能把自己伪装成 admin。前端不执行 SQL、不重新计算指标，也不在总结失败时编造答案。

当前 v0.1 已经可以在本地真实数据库和真实模型上演示，但仍是本地可信身份、小规模种子和 development 评测。正式登录、生产部署、高并发、监控告警、备份恢复、独立答案评审和 frozen holdout 验收属于后续边界。
