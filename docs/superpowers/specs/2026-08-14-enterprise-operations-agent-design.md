# 企业经营分析 Agent 升级设计

## 目标

将零售运营可审计数据分析 Agent 升级为一个面向企业经营分析的单 Agent Runtime。系统以零售业务作为真实落地场景，同时处理 PostgreSQL 结构化数据和企业制度 RAG，能够选择业务 Skill、规划多步任务、管理服务端上下文、调用受治理工具，并生成带数据证据和文档引用的经营复盘报告。

本次升级的求职目标是让项目能够真实展示 Agent 工程能力：Context Engineering、Skill 路由、Tool Registry、SQL/RAG 联合分析、Checkpoint 恢复、MCP 外部工具接入、Trace 和分层评测。所有简历数字必须来自提交后的 development 评测或可复现实验，不预设提升幅度。

## 范围

### 主任务

首个端到端演示任务为“退款异常诊断与经营复盘”：

> 最近 30 天指定区域的退款率为什么变化？结合渠道、商品和企业售后制度给出证据充分的复盘报告。

系统支持四个业务 Skill：退款异常诊断、渠道对比分析、商品表现分析、经营周报。第一阶段优先保证退款异常诊断闭环，其余 Skill 复用相同接口和工具治理层。

### 内部能力

- PostgreSQL 查询、指标语义校验、SQLGlot AST 安全校验、业务一致性校验、审批和查询审计。
- 项目二的企业知识检索能力，通过受权限控制的内部适配器提供 BM25/向量/RRF/Reranker、版本、生效时间、父文档路由、引用校验和拒答。
- Context Builder 负责任务目标、Skill、子任务、工具结果、RAG 证据、权限和 Token 预算的分层装配。
- Tool Registry 统一管理本地数据库、知识检索、图表和报告工具。

### 外部扩展

只实现一个有业务价值的 MCP 外部工具：报告模板/文件导出服务。核心 SQL 和 RAG 不通过 MCP 绕行；MCP 用于证明外部工具发现、Schema、权限、超时、Trace 和失败处理。

### 不做

- 不拆成多 Agent 团队。
- 不做通用插件市场或动态代码执行沙箱。
- 不把项目二完整复制进项目一；保留项目二仓库并使用稳定内部 HTTP/适配器边界。
- 不修改已经消费的 frozen holdout，不用 frozen 结果调参。

## 架构

```text
用户问题
  -> 会话/任务入口
  -> 领域识别与 Skill Router
  -> TaskPlan（目标、子任务、完成条件、预算）
  -> Context Builder（短期、会话、证据、权限层）
  -> Tool Registry
       -> PostgreSQL 查询工具
       -> 企业知识检索工具（项目二）
       -> 图表工具
       -> 报告模板/导出 MCP 工具
  -> LangGraph 状态执行
       -> 根据中间证据继续、补查、审批或拒答
  -> Report Composer
  -> 结构化报告、引用、Trace、指标
```

### 状态边界

LangGraph State 保存单次任务的可恢复执行状态；服务端 Conversation Store 保存跨请求会话和摘要；Evidence Ledger 保存带来源的事实；Execution Trace 保存节点、工具、模型、耗时、Token 和错误。四者不混为一个历史字符串。

### 上下文策略

- 当前任务层：用户目标、当前子任务、最近工具结果。
- 会话层：最近对话、已确认筛选条件、冲突条件和上轮结论摘要。
- 证据层：SQL 查询结果引用、指标版本、RAG source_id、有效时间和权限标签。
- 长期层：只保存用户明确确认的偏好，例如默认时间范围或关注渠道；不保存未经确认的模型猜测。
- Context Builder 根据 Token 预算裁剪原始历史，优先保留当前目标、约束和证据，较早轮次替换为摘要。

### 工具治理

每个工具有名称、描述、输入/输出 Pydantic Schema、权限要求、风险等级、超时、重试策略、是否有副作用和 Trace 元数据。未注册工具不能被 Agent 调用；越权直接拒绝，有权但高风险的数据库查询进入现有人工审批。

## 数据与评测设计

### 评测数据

首轮新增约 300 个 development 样本：80 条单轮经营问题、50 条多轮追问、40 条 RAG 制度任务、40 条 SQL/指标任务、30 条权限任务、30 条工具异常任务、30 条完整复盘任务。每条样本包含期望 Skill、子任务、允许工具、证据需求、关键结论、权限标签和拒答规则。

不读取或修改现有 frozen holdout 作为调参依据。升级后的 Agent 使用独立 development 数据和新的版本化验收集；如需新的冻结集，必须在代码、Prompt、语料和默认策略提交后一次性消费并保存原始报告。

### 指标

- Skill 路由准确率、子任务完成率。
- 工具选择准确率、工具参数正确率、多余工具调用率。
- SQL 执行成功率、SQL 业务正确率、数值结果一致率。
- Recall@5、引用准确率、证据覆盖率、权限泄漏率。
- 多轮条件继承准确率、上下文污染率、摘要关键信息保留率。
- 完整报告任务完成率、失败恢复率、Token 用量、p50/p95 延迟。

### 基线

至少保存三组可比较结果：现有固定工作流、加入 Skill/任务计划、加入 Context Builder 与多源证据。比较时固定模型、数据、Prompt 版本和运行环境，只改变待评估能力；所有结果保存原始样本级记录、聚合报告、配置指纹和代码提交。

## 失败与安全

- 任务预算、模型重试和工具重试均有上限。
- 越权字段、不可见文档、无权限 MCP 工具直接拒绝。
- RAG 或 SQL 证据不足时不生成确定性结论。
- MCP 工具失败不影响核心查询结果，报告明确标注缺失的外部能力。
- SSE 连接只是订阅通道，任务状态由服务端保存；断线可按任务 ID 查询状态和 Trace。
- 所有工具调用和报告结论关联 request_id、conversation_id 和证据 ID。

## 验收标准

1. 退款异常诊断能够在本地和公网配置下完成“数据查询 + 知识检索 + 图表 + 引用报告”闭环。
2. 至少一个多轮任务能继承筛选条件并在上下文预算内完成。
3. 至少四个 Skill 通过同一 Registry 注册，其中两个有独立评测样本。
4. 至少四个内部工具通过统一 Schema、权限、超时和 Trace 执行。
5. 一个 MCP 外部工具能被发现、调用、失败重试并在 Trace 中呈现。
6. 新增 Agent development 评测保存样本级原始记录和聚合指标；没有未经实测的提升数字。
7. 项目一原有测试和安全边界不回退；项目二已有 frozen 结果保持只读。
8. README、架构图、部署说明、项目讲解和面试问答与实际代码一致。
