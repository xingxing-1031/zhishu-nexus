# 企析企业 AI 工作台前端重构设计

## 1. 目标

将当前以卡片和流程展示为主的分析控制台，重构为真实企业内部使用的混合式 AI 工作台。

核心体验是连续对话。经营分析图表、结果表格、知识引用和风险提示作为回答的一部分呈现；Agent 执行过程、SQL、工具调用和审计信息通过渐进式披露查看。

本次重构不改变后端 API、Agent 路由、审批语义、权限模型或数据口径。

## 2. 设计原则

1. 回答优先：用户首先看到结论，不需要先理解 Agent 工作流。
2. 证据可查：数据、知识引用、工具调用和审核状态始终可以追溯。
3. 渐进披露：普通用户默认看到必要信息，技术细节按需展开。
4. 企业效率：界面安静、紧凑、可扫描，不使用营销页式装饰。
5. 状态明确：进行中、成功、降级、待审批和失败均有明确文字与恢复操作。
6. 响应式一致：桌面端、平板和手机端保留同一任务模型，只调整导航和详情面板形态。

## 3. 信息架构

### 3.1 桌面端

页面采用三栏结构：

- 左侧会话导航栏：品牌、新建对话、历史会话、管理员入口和账号操作。
- 中间对话工作区：消息流、内嵌分析结果、任务状态和固定输入框。
- 右侧证据检查器：知识引用、执行过程、数据口径、SQL、审核和审计信息。

右侧检查器默认可见，但允许用户关闭。关闭后中间对话区扩展，不保留空白占位。

### 3.2 平板端

- 左侧会话导航保持窄栏或抽屉形态。
- 中间对话区占据主要宽度。
- 右侧证据检查器改为覆盖式抽屉。

### 3.3 手机端

- 顶部应用栏负责打开会话抽屉和当前任务详情。
- 对话内容使用单列布局。
- 证据检查器改为底部详情面板。
- 输入框固定在安全区域上方。
- 图表在窄屏下简化坐标和标签，表格保留横向滚动容器。

## 4. 主要交互

### 4.1 空会话

空会话只展示产品名称、能力说明和少量真实任务示例，不展示大面积 KPI、营销文案或功能介绍卡片。

示例任务覆盖：

- 企业制度查询。
- 经营数据分析。
- 知识与数据联合判断。
- 时间、天气、网页摘要等通用工具。

### 4.2 消息流

- 用户消息使用紧凑的右侧消息块。
- 企析回答左对齐，正文不放入厚重卡片。
- 每轮回答包含状态栏、主要结论和可选结果模块。
- 历史回答保留在同一消息流中，新请求不得覆盖上一轮内容。
- 长回答使用清晰的小标题、列表和段落，不使用密集的小字号元数据。

### 4.3 执行状态

请求开始后，回答位置立即出现任务占位和当前状态，例如“正在检索企业知识”。

默认只显示当前阶段与完成状态。点击“查看过程”后，右侧检查器切换到执行标签，展示 Supervisor 路由、Agent 节点、工具调用和耗时。

状态动画只使用透明度和位移，必须支持 `prefers-reduced-motion`。

### 4.4 回答内容

回答按照以下优先级组织：

1. 直接结论。
2. 关键发现或风险说明。
3. 图表和结果表格。
4. 建议或下一步。
5. 数据口径和知识引用入口。

只有存在对应数据时才显示图表、表格、报告或引用模块，不保留空壳卡片。

### 4.5 证据检查器

证据检查器包含三个标签：

- 引用：企业知识原文、版本、生效时间和相关度。
- 执行：路由模式、Agent 步骤、工具调用、耗时和失败信息。
- 审计：指标口径、数据证据、SQL、审批状态和请求编号。

点击回答中的引用标记或“查看依据”，自动打开检查器并定位到对应内容。

### 4.6 输入区

- 支持多行输入。
- Enter 发送，Shift+Enter 换行。
- 请求执行期间禁用重复提交，并提供明确的进行中反馈。
- 输入区显示“自动选择能力”，不要求用户手动选择 Agent。
- 可以显示当前会话的上下文状态，但不暴露内部思维链。

### 4.7 审批

高风险请求在当前回答中显示待审批状态条。管理员可以从状态条打开审批面板。

审批面板继续展示 SQL 预览、敏感字段、请求指纹和拒绝原因。关闭面板不改变审批状态，批准或拒绝后回到原消息位置更新结果。

## 5. 视觉系统

### 5.1 色彩

- 页面背景：`#F6F7F9`
- 主要表面：`#FFFFFF`
- 主要文字：`#17202E`
- 次要文字：`#53606F`
- 弱化文字：`#7B8794`
- 品牌主色：`#0F766E`
- 品牌交互色：`#0B625C`
- 数据强调色：`#2563EB`
- 成功色：`#15803D`
- 警告色：`#B45309`
- 危险色：`#C2413B`
- 默认边框：`#DDE2E7`

品牌色负责导航、焦点和主要操作；数据蓝用于图表和数据入口。语义色必须同时配合文字或图标，不得只依赖颜色表达状态。

不使用紫粉 AI 渐变、玻璃拟态、装饰光球或大面积深色背景。

### 5.2 字体

字体栈使用 `Inter`、`PingFang SC`、`Microsoft YaHei UI`、`Noto Sans SC` 和系统无衬线字体。

- 页面标题：20px / 28px，600。
- 回答正文：15px / 25px，400。
- 导航与控件：14px / 20px，500。
- 辅助信息：13px / 18px，400。
- 元数据：12px / 17px，400。

SQL、请求编号、耗时和数值使用等宽字体与等宽数字。除必要元数据外，不使用小于 12px 的文字。

### 5.3 形状与层级

- 常规圆角为 6px，面板和抽屉最大 8px。
- 不使用页面区块套页面区块的嵌套卡片。
- 主层级通过边框、留白和背景差异建立。
- 阴影只用于浮层、抽屉和固定输入区，不作为常规卡片装饰。
- 所有图标统一使用 Lucide，图标按钮提供可访问名称和悬停提示。

## 6. React 组件边界

保持 `App.tsx` 的会话、登录和管理员页面路由职责，重构工作区组件：

- `WorkspaceShell`：桌面、平板和手机端整体布局。
- `ConversationRail`：新建会话、历史会话和工作区导航。
- `ChatThread`：连续消息列表、滚动位置和空会话状态。
- `UserMessage`：用户消息展示。
- `AssistantResponse`：企析回答和结果模块编排。
- `AgentProgress`：紧凑任务状态和展开入口。
- `InlineChart`：懒加载 ECharts 图表。
- `ResultTable`：响应式数据表格。
- `EvidenceInspector`：引用、执行和审计标签。
- `MessageComposer`：输入、快捷键、提交与加载状态。
- `ApprovalSheet`：审批详情和操作。

API 类型和响应模型保持不变。前端将每次 Agent 响应保存为会话消息，从响应中派生回答模块和检查器内容。

## 7. 数据与状态流

1. 用户提交问题，立即追加用户消息和运行中的企析消息。
2. 前端调用现有 Agent 接口并接收执行状态或最终响应。
3. 状态事件更新当前企析消息的进度，不创建额外页面级流程卡片。
4. 最终响应写入消息，并生成图表、表格、引用和审核入口。
5. 点击引用或执行详情时，只更新检查器选择状态，不重新请求分析。
6. 切换历史会话时恢复消息、滚动位置和检查器状态。

## 8. 错误与空状态

- 网络失败：显示失败原因和“重新执行”按钮，保留原问题。
- 服务未就绪：输入区禁用，并显示可恢复的服务状态说明。
- 任务降级：正常展示已有结果，同时明确缺少的数据或证据。
- 无数据：显示当前筛选条件下没有结果，并提供调整问题的建议。
- 图表失败：保留表格和文字结论，不让整个回答失败。
- 引用不可用：回答标记证据不足，不显示空引用面板。
- 审批等待：显示等待状态，不把任务误标为失败。

## 9. 性能与可访问性

- ECharts 和管理员页面按需加载。
- 避免在每次输入时重新渲染完整历史消息。
- 异步结果区域预留稳定空间，减少布局跳动。
- 所有可操作元素支持键盘访问和可见焦点。
- 图标按钮必须有 `aria-label` 或可见文字。
- 正常文字对比度不低于 4.5:1。
- 图表必须提供文字摘要和表格替代。
- 桌面最小点击目标 24px，触屏目标不低于 44px。
- 支持 375、768、1024 和 1440 像素宽度。

## 10. 验证方案

- 运行 TypeScript 和 Vite production build。
- 运行现有前端 smoke 测试。
- 验证登录、退出、新建会话、历史会话、普通对话、知识查询、数据分析、协作分析和审批流程。
- 在 1440x900、1024x768、768x1024 和 390x844 视口检查布局。
- 检查长中文回答、长请求编号、空数据、错误、降级和待审批状态。
- 检查键盘焦点、Enter/Shift+Enter、抽屉关闭和 reduced-motion。
- 部署后对线上页面重复关键流程验证。

## 11. 验收标准

1. 首屏以对话任务为中心，不再以 KPI 和流程卡片为中心。
2. 一般问题无需打开执行详情即可完成阅读。
3. 任何数据和制度结论都能在两次操作内查看证据。
4. 多轮对话不会覆盖先前回答。
5. 桌面端可同时查看对话和证据，手机端可以通过底部面板查看证据。
6. 页面不存在小于 12px 的必要正文，也不存在不可访问的图标按钮。
7. 后端接口、权限、审批、审计和数据口径行为保持兼容。
8. production build、smoke 测试和线上关键流程验证全部通过。
