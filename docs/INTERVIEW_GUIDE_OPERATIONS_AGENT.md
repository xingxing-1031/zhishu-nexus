# 企业经营分析 Agent 面试讲解

## 一句话介绍

我把原来的可审计 Text-to-SQL 工作流升级成一个单 Agent 企业经营分析 Runtime：它先把问题路由到业务 Skill，再生成有界 TaskPlan，使用服务端上下文和统一 Tool Registry 调用 PostgreSQL 与企业制度 RAG，最后输出带数据 source ID、制度引用、限制说明和 Markdown 导出的经营复盘报告。

## 主流程

1. 用户提出“最近 30 天退款率为什么变化，结合售后制度复盘”。
2. Skill Router 选择 `refund_diagnosis`，TaskPlanner 生成趋势、拆解、制度证据和报告等有界子任务。
3. ContextBuilder 按“当前目标/约束 -> 证据 -> 最近工具结果 -> 摘要 -> 历史原文”装配上下文，并设置 Token 上限。
4. Tool Registry 校验每次调用的 Pydantic Schema、角色、风险等级、超时和幂等键。
5. `sql.query` 复用原有 SQLGlot AST 只读校验、指标/JOIN/时间范围业务一致性校验、审批和 PostgreSQL 只读执行。
6. `knowledge.search` 通过项目二受令牌保护的 `/internal/evidence` 获取权限过滤、版本和生效时间明确的制度证据；项目二继续负责 Rerank、引用边界和权限。
7. ReportComposer 把 SQL 结果与制度引用合并成结构化报告；可选 `report.export` 通过官方 MCP Python SDK 导出 Markdown。

这里有一个重要的任务拆分边界：SQL 工具接收包含时间、指标和维度的结构化数据问题；RAG 工具接收 Skill 专属的制度问题。例如退款诊断会单独检索“退款风险、人工复核条件和经营复盘要求”，不会把“按退款状态统计退款金额”误当成知识库必须覆盖的制度事实。

## 高频追问

### 为什么不是把 RAG 也封装成 MCP？

RAG 是核心证据链，必须稳定参与主链路、保留项目二的权限和引用边界，因此使用内部 HTTP Evidence API。MCP 选择报告导出这种可替换的外部工具，展示工具发现、Schema、调用失败降级和协议接入能力，不让协议层绕过核心安全边界。

### 上下文如何控制？

服务端按 conversation ID 和 user ID 隔离保存结构化对话、确认约束、证据 ID 和摘要，不保存模型隐式思考。ContextBuilder 用确定性 Token 估算，优先保留当前目标和证据，预算不足时截断旧历史并在响应中标记 `truncated`。

### 如何处理恢复和副作用？

LangGraph checkpoint 只在节点边界保存可恢复状态；工具调用带 `request_id`、conversation ID 和输入指纹。幂等工具复用相同结果，邮件/导出等副作用必须有稳定幂等键，避免恢复时重复执行。Trace 解释运行过程，Audit 记录责任和追溯，两者不混用。

### SSE 和任务状态是什么关系？

SSE 只是订阅通道，前端断开不会取消服务端线程中的任务；任务状态和工具结果由服务端保存。重新打开页面应按 conversation/task ID 查询状态或继续订阅，不能把一个浏览器连接当作任务生命周期。

### 为什么周报 Skill 要补默认指标？这算不算替用户猜需求？

`weekly_report` 本身就是一个有明确输出契约的业务 Skill。用户说“经营周报”时，Agent 会给 SQL 工具补充“按渠道统计销售额和订单数”的最低数据口径，时间范围仍来自原问题；不会自动加入利润、库存等数据库不存在的指标。这个默认值写在可测试的 Skill/工具契约中，比把模糊问题原样交给模型临场猜测更稳定、也更容易审计。

### 为什么 SQL 和 RAG 不能直接使用同一个完整问题？

复合问题包含两种证据需求：结构化数据和制度规则。完整问题交给 SQL 是合理的，因为它需要时间、指标和维度；完整问题交给 RAG 会使检索规划器把“统计退款金额”也拆成必须由制度文档覆盖的 need，最终即使召回正确退款制度也可能因缺少结构化数据证据而拒答。Agent 层应先拆任务，再让每个工具只完成自己的职责。

### 11/12 是否可以说成 Agent 准确率 91.7%？

不可以。它是 12 条线上 development 样本的逐题契约通过率，样本已用于定位问题；只能描述具体条件和分项结果。更稳妥的说法是：Skill 路由、工具选择、证据要求、拒答和上下文预算均为 12/12，8 条业务题全部得到成功或可信降级，唯一未完全通过样本是总结服务降级，但 SQL 行数据和证据被保留。

### 为什么一个样本是 degraded，但没有丢数据？

系统把数据库执行和自然语言总结分开。该样本中 SQL、制度检索和 MCP 导出都成功，模型总结暂时不可用时，工作流返回固定降级说明和可信 rows，而不是重新编造结论或把整条任务标成失败。这是“可信结果优先于流畅回答”的设计。

### 目前哪些数字能写在简历？

项目一可以写：12 条公网 live development 中逐题契约通过 11/12；Skill 路由、工具选择、证据要求、拒答和上下文预算均为 100%；8 条业务题全部成功或可信降级，端到端 P95 为 29.535 秒。必须同时说明这是 development，不是通用准确率。

发布性能可以写：通过 Git bundle、Docker 依赖层缓存和区域 PyPI 镜像，将一次超过 13 分钟仍未完成的发布，降到最近三次完整 GitHub Actions 发布 50-58 秒，均值约 55 秒。不要写成模型推理性能提升。

项目二可以单独写已保存并可复现的 frozen holdout：8 条、执行成功率 75%、核心通过率 62.5%、Recall@5 100%、引用准确率 85%、权限泄漏率 0%、P50/P95 6.93s/41.45s。两个项目的样本和指标不能混成一个“综合准确率”。
